# Security and privacy

The production dashboard requires a password. Reporters use separate, source-bound bearer tokens; an agent token cannot read the dashboard or impersonate another source. Passwords use salted scrypt, sessions use HttpOnly/SameSite cookies, and HTTPS deployments use Secure cookies. Login and ingestion have rate limits. The hub binds only to loopback; put an HTTPS tunnel or trusted reverse proxy in front of it. Do not disable authentication at the proxy or remove application authentication.

Telemetry contains hostnames, OS usernames, process names, PIDs, resource usage and (optionally) Slurm jobs. Treat it as private. Full process command lines, environment variables, Slurm working directories and commands are not collected. Process names and job metadata can still contain sensitive information. OS permissions determine which processes are visible; never elevate privileges to bypass them.

Only the latest snapshots are persisted, with mode 0600. Configuration, enrollment tokens, login credentials, PM2 state and logs must stay outside the repository. PM2 dump files and backups may contain sensitive paths and configuration. Git ignore rules are defense in depth, not a replacement for reviewing staged files.

The service worker caches only public assets and an offline placeholder. It does not cache authenticated HTML or API responses. Logging out revokes the current session; restarting the hub invalidates all sessions. Each session identifies a user, and GPU/CPU/RAM and Slurm queries are owner-scoped. Administrators can create, disable and reset user accounts. Device ownership is checked on every management operation; administrators do not automatically see other owners’ telemetry. The admin-only `/api/users/devices` inventory explicitly returns only owner username, device display name and distinct last-known GPU model names; no live metrics, process details, timestamps, device IDs or credentials are returned. This is application-level isolation, not a separate OS sandbox for each account. There is no historical metrics database or audit trail.

Use **My devices → Remove device** to revoke reporting and remove its hub snapshot. Removing an account's access, changing a password or resetting it invalidates the appropriate sessions. A disabled account's agents cannot report; re-enabling it permits their existing tokens again. Keep the private accounts file backed up. See [the account recovery procedure](docs/USER_MANAGEMENT.md) for offline password reset; legacy top-level password hashes stop being authoritative after migration.

Install links are short-lived bearer capabilities, hashed at rest, owner/device/origin-bound and consumed atomically by enrollment. GET requests do not consume them. Generating a replacement invalidates older tickets; redeeming it rotates the reporting token. Long-lived tokens are never included in the URL or shell command. Prevent reverse proxies from retaining `/install/*` paths in access logs, and never publish an installation link. The installer requires HTTPS, refuses root, rejects redirects and downloads an explicit file allowlist from the trusted hub. Source hashes are integrity checks, not protection from a compromised hub.

`npm run demo` serves only invented fixture data and has no authentication. It is bound to loopback and is separate from the production server. Never adapt it to serve real data or expose it as a production deployment.

For a vulnerability, use the repository's private vulnerability reporting channel if available. Otherwise open a minimal issue asking for a private contact; do not post credentials, exploit payloads against a live deployment, or private telemetry publicly.
